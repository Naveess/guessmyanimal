## Design Specificity Verdict

## Overall Impression

The splash has real craft and a real point of view — the paw stamp alone is worth more than most "hero animations." But the two assessments (design review and mechanical evidence) disagreed on one load-bearing claim, and I verified it myself before writing this up: **the search box is genuinely invisible on first paint, not just theoretically slow to appear.** `.home` is `min-height: 100svh`; `#searchunit` sits as a plain DOM sibling *after* `.home` closes, with no absolute positioning; it only gets moved into the hero by `dock('home')`, which is called from `goHome()` at the very end of `app.js`'s boot sequence — the last of eight synchronous, non-`defer`/non-`async` `<body>` scripts. Until all seven scripts before it finish, `#q` exists in the DOM (technically focusable) but renders below the fold, off-screen. For the exact scenario PRODUCT.md names as primary — a moving car, a pub, no reliable focus time — the one thing that has to be instantly there is the one thing that isn't, until the JS chain clears. That's the single biggest opportunity here: not a redesign, a sequencing fix.

## What's Working

1. **The paw stamp.** A multi-part, physically-authored animation (fall, squash-on-contact, ripple, dust, letters knocked loose by the shockwave) that's replayable on tap — the system's entire authored-motion budget spent on the one moment that deserves it.
2. **Starter chips that actually track usage.** `STARTERS` swaps to a `localStorage`-backed "jump back in" list (with the label text changing too) once someone has looked something up mid-game — a real behavioral adaptation, built without accounts or tracking.
3. **The honest empty-search state.** "No match for 'x'. It might not be in here yet — there are 435 so far" — specific, calm, non-blaming. Exactly the tone PRODUCT.md commits to.

## Priority Issues

**[P1] Search box is off-screen on first paint, exactly when speed matters most**
- **Why it matters**: PRODUCT.md's stated primary context is a car, a pub, low reliable focus time — a confident answer "in about four seconds." The one control the whole product exists to make fast is invisible until 7 blocking scripts (`animals.js`, `render-data.js`, `related.js`, `game-core.js`, `vendor/qrcode.js`, `party.js`, `mystery.js`) finish and `app.js`'s boot IIFE runs `routeFromURL()` → `goHome()` → `dock('home')` (index.html:859–877; app.js boot tail). On a slow or interrupted connection, a visitor sees the wordmark and dead space, with the actual task entry point sitting below the fold.
- **Fix**: Give the hero its default (pre-JS) DOM position for `#searchunit` — nest it inside `.home-in`/`#dockHome` in the markup itself — and use JS only to relocate it *out* into the top bar once an animal is showing, reversing today's default direction of movement.
- **Suggested command**: `/impeccable optimize`

**[P1] The documented focus-ring spec is structurally impossible on the two primary text inputs**
- **Why it matters**: DESIGN.md states the search field's focus treatment is "a border-strength change plus the standard 3px focus-visible outline for keyboard users." In the actual CSS, `#q { border: 0; outline: none; }` (style.css:481–488) and `#partyCodeInput:focus { outline: none; }` (style.css:1373) are ID/ID+pseudo-class selectors (specificity 1,0,0 / 1,1,0), which beat the global bare `:focus-visible { outline: 3px solid ...}` (style.css:142, specificity 0,1,0) regardless of source order. The 3px outline the design system promises can never render on either input — a keyboard user tabbing to the one input this whole product is built around gets only a 1px border-color shift as feedback.
- **Fix**: Scope the suppression correctly — `#q:focus { outline: none; }` should not exist at all if the intent is "border-strength change *plus* the standard ring"; either let `:focus-visible` win by removing the ID-level `outline: none`, or explicitly redeclare the 3px ring inside `#q:focus-visible`.
- **Suggested command**: `/impeccable audit`

**[P2] Three confirmed sub-guideline touch/contrast targets on this screen**
- **Why it matters**: `.home-code-link` ("Have a party code?") has no `min-height` at all — just `padding: 4px` around 13.5px text, ≈24px effective tap height against the 44px guideline (style.css:1349–1354). `.theme-btn` (the System/Light/Dark buttons inside the mobile corner menu, visible at every width) is `min-height: 38px` (style.css:2305). The `.chip` border — the only visual affordance that these are tappable, not just labels — is `color-mix(in srgb, var(--home-ink) 24%, transparent)` on solid Sun, which computes to roughly **1.60:1** against WCAG's 3:1 floor for UI boundaries (style.css:446), i.e. the outline is nearly invisible even though the text inside it reads fine.
- **Fix**: Raise `.home-code-link` and `.theme-btn` to 44px min-height; raise `.chip`'s resting border opacity (not just its `:hover` state, which a touchscreen never triggers) closer to 40–45%.
- **Suggested command**: `/impeccable audit`

**[P2] Starter chips break the site's own ARIA-grouping pattern**
- **Why it matters**: `#starterChips` (index.html:193) has no `role="group"` / `aria-labelledby`, even though the exact same pattern — a label with an `id`, a control group pointing back at it via `aria-labelledby` — is correctly used one component away for `.theme` (`id="themeLabel"` / `aria-labelledby="themeLabel"`, index.html:104–105). A screen-reader user tabbing through the splash hears four unlabeled buttons with no announced context that they're suggestions.
- **Fix**: Add `role="group" aria-labelledby="startersLabel"` to `#starterChips`, mirroring the theme toggle exactly.
- **Suggested command**: `/impeccable audit`

**[P2] Three near-equal-weight "primary" actions dilute the one decisive moment**
- **Why it matters**: DESIGN.md calls `.mystery-play` "the splash's one primary action," but the search box sits directly above it at equal or greater visual weight (largest tap target on the screen, `--shadow-l`, stark card-on-yellow contrast), and the starter-chip cluster sits between them. A first-time visitor unfamiliar with the product's two-track nature (look something up vs. play a round) has no clear signal which of three loud surfaces to press first — working directly against the product's own 4-second promise.
- **Fix**: Mute `.mystery-play` toward the `.chip`/`.play-link` quiet-outline register, or add one line differentiating "look one up" from "play a round" before the visitor has to guess from visual weight alone.
- **Suggested command**: `/impeccable layout`

## Persona Red Flags

**Casey (distracted mobile)**: On the slow/flaky connection that's Casey's default context, the hero shows a wordmark and dead space — no search box, no chips, no counter — until 7 render-blocking scripts finish (P1 above). Even once loaded, three co-equal-weight surfaces (search / chips / Mystery Animal) cost Casey the extra second of "which do I tap" that the product's own 4-second promise can't afford.

**Sam (accessibility)**: Tabbing to the search field — the one control the entire product exists to make fast — produces only a 1px border shift, not the 3px outline DESIGN.md itself promises, because of the specificity bug above. The starter chips announce as four context-free buttons with no group label. `.theme-btn` in the mobile menu (System/Light/Dark) sits at 38px, under the 44px floor, in a menu Sam is more likely to navigate carefully rather than skim.

**Jordan (first-timer)**: Never having used the product, Jordan lands on three visually loud, un-differentiated options (type something / tap a chip / play a round) with no cue for which one is "the" thing to do first — exactly the ambiguity the "one primary action" design principle was meant to prevent.

## Minor Observations

- The Mystery Animal button's discoverability nudge (a timed shake, per its own code comment: "a real problem a real player ran into") is fully stripped by `prefers-reduced-motion` with no static compensation (style.css:1387–1394) — the one feature added specifically to fix a discoverability gap loses its effect for exactly the population most likely to need a non-motion cue instead.
- `#partyCodeInput::placeholder` computes to ~2.84:1 in light mode (style.css:1369–1371) — under even the 3:1 large-text floor, though it's placeholder text on a low-stakes field.
- Submitting the party-code form empty surfaces the same "check for typos" message as a garbled code (party.js) — mildly inaccurate, low-stakes.
- The 620px breakpoint documented in DESIGN.md for the search row could not be confirmed to affect anything on this specific screen — every rule found under that query targets the animal-detail feed, not `.home`/`.searchrow`.
- The site's own stated honesty commitment ("some judgment calls are arguable and may be wrong") never appears on the splash itself — it's one tap away via "How it works," so a first-time visitor's very first impression carries none of that trust signal.
